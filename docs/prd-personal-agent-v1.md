# Today Personal Agent 第一版产品需求（讨论稿）

状态：细化讨论稿；不代表功能已实现。第 1-6 节为已讨论的方向，第 7-12 节为据此提出的实施口径，需产品评审确认；第 13 节列出待决策项。

## 1. 产品定位与目标

Today 是用户手机上的个人 AI Agent。首版采用同一套跨平台移动端代码支持 Android 与 iOS；先交付 Android 安装包开展小范围试用，之后发布 iOS 版本，不把 iOS 适配留到 Android 完成后重写。用户可以自定义一个非真人、但有性格的陪伴形象；它通过持续对话理解用户，在获得相应授权后记住重要内容、主动跟进，并帮助用户使用 Today 内部的记录与行动工具。

第一版验证三个问题：用户是否愿意持续与自定义形象对话；是否认为有缘由且有分寸的主动跟进有价值；是否愿意让 Agent 帮忙把对话转化为每日记录和具体行动。

现有的每日记录、总结、时间轴、长期记忆、待办、习惯打卡和提醒是第一版可复用的基础能力。本需求新增的对话、形象、自动识别关注点和站内主动跟进均未在当前仓库中完成。当前仓库只有 Next.js Web 与 Java API，没有移动端工程；Web 的服务端 API 代理也不能直接作为离线打包页面运行，移动端接入和站内消息能力需要单独设计和开发。现有的站内主动提示和提醒投递不等于完整的 Agent 跟进收件箱。

## 2. 体验原则

- Today 提供可直接使用的默认形象，但不预设不可改变的人格；用户可自行修改 Agent 的形象、名称和交流风格。修改后，已保存的对话、记录和记忆仍归属于同一用户。
- Agent 可以判断什么值得关注，但对话内容不会默认变成每日记录、长期记忆或跟进授权。
- 主动联系仅指应用内的跟进消息，必须有可说明的缘由。没有值得跟进的内容时不生成泛泛问候；用户可设置频率上限、暂停跟进或停止某个话题的跟进。应用关闭时不发送系统通知。
- Agent 能读取并建议操作 Today 内部数据；写入、修改和删除须让用户看到具体影响并确认。对外发送和操作手机其他应用不在本期范围。
- 明确告知用户它是 AI，不冒充真人或心理咨询师。提供情绪支持，但不进行诊断或治疗承诺；高风险表达须进入专门的安全响应流程。

## 3. 第一版范围

### 3.1 自定义陪伴形象

首次进入时展示一个默认的非真人陪伴形象，用户可以直接开始对话，也可以立即修改；后续可随时从手机相册上传图片作为自定义形象，并编辑名称和交流风格。默认形象只是可替换的起点，不强制用户使用某种固定人格。上传图片与现有的习惯照片打卡是不同功能。默认形象可有少量倾听、思考和回复状态反馈；用户上传的静态图片不要求生成动画、口型或表情。动态效果可关闭，遵循系统减少动态效果设置；形象不得阻挡阅读和操作。

用户上传图片后可裁剪、预览并确认，也可更换或恢复默认形象。首版不要求通过文字生成形象、从上传图生成新角色或提供复杂捏脸；图片格式、尺寸与内容规则由技术设计细化。不以实时 3D 或口型同步作为第一版前提。

### 3.2 持续对话

- 用户以文字主动发起和继续对话，历史对话可查看；Agent 回复可以参考用户已保存且允许使用的记录、记忆和当前会话上下文。首版不包含语音输入或语音播报。
- 用户可纠正 Agent 的理解，要求不要保存或继续提起某个话题。回答应区分用户说过的事实、Agent 的推测和尚待确认的信息。
- 对话可以围绕日常经历、情绪困扰、目标和具体事务展开，但不把每轮交流都包装成待办或心理分析。
- 对话的保留、删除和隐私设置应可被用户理解和管理；跨对话使用哪些信息，应与长期记忆的授权规则一致。

### 3.3 对话整理为每日记录

用户可主动要求“整理进今天”，Agent 也可在合适时提议。Agent 生成可编辑的预览，展示原话依据和整理后的内容；只有用户确认后，才创建或补充当天的每日记录。放弃时不写入。

同一天沿用现有的一日一条记录语义：若已有记录，先展示将如何补充或改写，确认后再更新，避免重复时间轴卡片。记录变更后重新生成对应总结，并使时间轴呈现最新结果；处理期间显示状态，失败时可重试，不把未成功的整理结果伪装成已完成。

“每日记录”与“习惯打卡”是两种不同操作。对话中提到完成某项习惯，不能未经确认就自动产生打卡记录。

### 3.4 长期记忆与关注点

Agent 可从对话或每日记录中提取候选信息，判断其是否稳定、对未来有用，以及是否值得后续跟进。候选信息不等于正式长期记忆：保存前展示提议并征得用户确认；用户可查看、修改、删除已保存内容，并知道它源自哪次对话或哪条记录。此规则也应覆盖原有的手动每日记录入口，不能只约束对话入口。

一次性情绪、未经证实的推断和敏感标签不应被固化成用户画像。用户明确表示“别记住”或“别再跟进”时，相关保存和主动联系应停止；删除后不能仅靠旧的候选结果再次恢复。删除对话采用逻辑删除，并清理它派生的记忆和关注点；物理清除期限等隐私规则仍需设计。

### 3.5 主动跟进

Agent 从对话中识别未结束、对用户重要且适合以后询问的内容，不预设只能关注某一类主题。需要能概括关注缘由、下次适合询问的时机，并判断话题是否已经结束或不宜跟进。

- 用户明确提出跟进请求时，展示拟跟进的内容和时间，确认后创建；一次性约定、每日定时提醒与一般主动联系分开管理。
- Agent 推断出值得跟进的内容时，先询问用户是否希望后续再聊；同意后，在授权的话题及频率范围内选择有意义的时机，不必每次重新授权。
- 普通主动联系受用户设置的频率上限约束；无合适理由时不生成。重要的明确约定不得悄悄被普通频率上限吞掉；暂停普通跟进时不新增普通跟进，已约定的提醒在站内仍可查看，并可单独取消。默认每自然周最多 3 条、每天最多 1 条、同一话题至少间隔 7 天；用户可调低上限或关闭。
- 每条主动消息说明缘由，并支持继续聊、稍后、停止该话题。用户不回应不代表同意继续催促；同一关注点不得频繁重复发送。
- 跟进和到期提醒保存在 Today 站内消息中：用户正在使用应用时可查看，应用关闭期间到期的内容在下次打开时可查看。未读消息不会因应用关闭或换设备丢失。首版不申请系统通知权限，不发系统通知或远程推送；站内提醒不承诺在应用关闭时准点告知用户。Android 和 iOS 遵守同一规则。

### 3.6 Today 内部操作

第一版 Agent 可查询用户授权范围内的今日记录、时间轴、长期记忆、待办、提醒与习惯打卡；可在对话中提议创建或修改待办、提醒、习惯配置和打卡记录，以及整理今日记录和保存记忆。

执行前展示操作对象、内容、时间和可能影响，由用户确认后执行；执行成功或失败都要反馈。提供可查看的操作记录，支持撤销技术上可撤销的操作。任何未经确认的模型回复不得冒充实际执行结果。跨应用操作、对外发送以及自动删除内容均不在第一版范围。

## 4. 关键用户流程与验收条件

1. **首次进入移动 App**：默认形象已可使用，用户可跳过自定义直接开始文字聊天，也可上传图片修改形象；对话记忆和站内跟进的授权分别说明，无需系统通知权限。Android 首发，iOS 流程保持一致。
2. **从对话留下今天**：Agent 提议或用户主动发起整理；预览可编辑、可取消；确认后当天记录、总结和时间轴更新，原对话保持可追溯。
3. **获得跟进授权**：Agent 从聊天发现一个待续话题，说明为什么想跟进；用户同意后能查看和修改它，拒绝后不因同一段对话再次反复提议。
4. **主动联系**：只有在授权和频率规则满足时才生成普通站内跟进；应用关闭时没有系统提醒，下次打开时仍可看到未读内容、缘由，并能继续聊、稍后或停止该话题。
5. **执行内部操作**：用户提出“明天提醒我做某事”或“记下这个待办”；Agent 给出具体操作预览；用户确认后 Today 中出现对应内容，失败时不声称已完成。
6. **纠错与删除**：用户可改正错误的每日记录或记忆，并停止某个话题的跟进；逻辑删除对话后，来自该对话的记忆、关注点和待投递跟进同步清理，后续对话与站内消息不再沿用已删除或已撤销的内容。

## 5. 安全、隐私与可用性

- 涉及自伤等高风险表达时，优先提供适当的危机应对指引，避免承诺保密、提供诊断或将风险对话变成营销式主动联系；具体安全策略上线前须评审。
- 用户可管理对话、长期记忆、跟进话题、操作记录和站内消息。只使用完成当前回应所需的数据；首版不向系统通知或锁屏展示对话内容。
- 手机端以可阅读、可操作为先：形象动画不应遮挡内容，状态变化有文字反馈，交互支持无动画模式和无语音模式。
- 明确区分“建议”“等待确认”“执行中”“已完成”“失败”，避免用户以为 Agent 已经替自己完成了未执行的事。

## 6. 不在本期与后续规划

独立的成长项目（目标、阶段、回顾等）是后续规划，不阻塞本期用待办、习惯和提醒支持具体行动。本期也不接日历、健康数据、邮件或其他手机应用；不做系统通知、远程推送、自主对外发消息、实时 3D、语音输入、语音播报、语音通话、心理诊疗或无限制的自动操作。iOS 正式发布晚于 Android 首发，但跨平台适配属于本期建设范围。

## 7. 目标用户与核心场景（建议口径）

面向愿意用手机简短记录生活、希望被持续理解，但不想维护复杂日记或目标系统的用户。首版优先覆盖以下四种场景：

| 场景 | 用户表达 | 期望结果 |
| --- | --- | --- |
| 想聊聊 | “今天很累，只想说说” | 先回应情绪，不强行生成任务或记忆 |
| 留下今天 | “把刚才说的整理进今天” | 展示可编辑预览；确认后更新当日记录与总结 |
| 以后再问 | “下周三问问我面试怎么样” | 展示一次性跟进提议；确认后到期进入站内消息 |
| 帮我行动 | “把准备材料记成待办” | 展示拟执行操作；确认后创建，失败可重试 |

不以“聊天次数”“每日打卡次数”作为唯一成功标准；重点观察用户是否完成自主对话、是否愿意确认记录，以及主动跟进是否被认为有帮助而非打扰。

## 8. 信息架构与页面（建议口径）

移动 App 首屏建议为“对话”，保留现有“今天”的独立快捷入口。Android 与 iOS 使用同一信息架构，但遵循各自的系统返回与安全区域行为。最少需要以下视图；具体底部导航数量和视觉方案在交互设计阶段确定，避免照搬当前 Web 的六项导航。

| 视图 | 用户可见内容与主要动作 |
| --- | --- |
| 对话 | 当前形象、消息流、文字输入、继续历史对话、由对话产生的确认卡；形象不压住消息和键盘 |
| 站内消息 | 未读跟进、到期约定和现有提醒的入口；按来源分组或标识，支持继续聊、稍后和停止跟进 |
| 今天 | 今日原文、总结状态、确认或改写、查看关联对话；记录未完成时显示重试状态 |
| 回看 | 时间轴和记忆入口；记忆可追溯来源、修改或删除 |
| 行动 | 待办、习惯打卡与已有定时提醒，支持查看 Agent 执行的结果 |
| 形象与设置 | 编辑外观、名称和交流风格；管理跟进授权、频率、会话数据及操作记录 |

从站内跟进点“继续聊”须进入相应话题的上下文；从今日记录或记忆可回到对应对话依据。Android 返回键和 iOS 返回手势都应先退出预览或详情，再回到原页面，未提交的输入应保留。

## 9. 详细功能与状态规则（建议口径）

### 9.1 形象与聊天

新账号自动拥有一个可立即使用的默认形象，不应强迫用户完成自定义才能说第一句话。可编辑字段至少包括名字、从相册上传的形象图片和交流偏好（例如更简短或更善于提问），用户可以以后再改，也可以恢复默认设置；但安全边界不随偏好改变。上传流程应支持裁剪、预览、取消、替换和上传失败后重试；失败时保留原形象，未确认的新图片不能生效。只在选择图片时请求相册访问，上传前展示图片仅用作形象的用途。外观和对话数据分离：更换形象不重写历史消息或记忆。

同一账号重新登录后能看到历史会话。发送文字后依次显示发送中、已发送、生成中和结果；网络失败可重试，不得重复写入用户消息或重复执行操作。上下文优先取当前会话与用户明确保存的记忆；历史对话不得默默成为新的长期记忆。无法确认事实时要询问，不以“我记得”伪造历史。

在情绪话题中先回应用户所说的具体处境，可询问对方是想倾诉、一起梳理，还是需要具体建议；用户没有提出行动需求时不主动把情绪转成打卡或待办。不以亲密承诺、过度拟人或“只有我懂你”制造依赖；用户随时可以结束对话或纠正回应方向。

### 9.2 今日记录、总结、时间轴

整理请求由用户主动触发，或由 Agent 在聊天节点提出；用户拒绝后本次对话不重复催促。确认卡至少展示拟写入日期、原话依据、可编辑正文、与当天原记录的合并结果。默认不覆盖已有正文；若需替换，明确提示替换范围。午夜跨日时明确展示按哪一天保存，允许用户在授权范围内改日期。

用户确认仅代表同意写入每日记录，**不代表同意写入长期记忆或建立跟进**。保存成功后触发日总结重算；时间轴使用同一日期的最新记录，不新增第二张卡。总结生成失败时保留已保存的原文，提供重试入口；重试不应重复创建记录或记忆。手动填写“今天”的原有入口遵守相同规则。

### 9.3 长期记忆

每个候选记忆展示文字、来源和保存用途，用户可编辑、确认或拒绝；同一来源的拒绝决定不应反复弹出。已确认的记忆有明确状态（有效、已归档或已删除）及来源。删除、修正或撤销授权后，后续检索与主动跟进不得使用旧版本。对话历史与长期记忆分开管理：删除记忆不必自动删除整段对话；删除会话时按下述来源清理规则处理派生内容。

删除会话是逻辑删除：会话及消息立即对用户不可见，并从模型上下文、搜索和继续对话入口排除。所有仅由该会话派生的候选/已确认记忆、关注点及其未发送跟进同步标记为失效，并从向量索引和生成候选的任务中移除；已投递的跟进保留必要的删除记录，但不再展示已删除的敏感正文或提供继续聊入口。若某记忆另有独立来源且用户曾分别确认，撤除本会话来源后可保留其独立版本；否则失效。用户另行确认创建的待办、每日记录或习惯打卡不随对话删除而删除，需在原模块单独处理。恢复会话（若后续提供）不得自动复活已清理的记忆或跟进。

### 9.4 关注点、一次性约定与站内收件箱

候选关注点至少包含：主题、依据、授权状态、下次适合的时间、结束条件和最近一次跟进时间。无明确时间时让用户选择或同意一个宽泛时段；不要凭空编造具体日期。状态建议为 `待确认 → 已授权 → 待触发 → 已投递 → 已处理/已结束`，拒绝与暂停为独立状态。用户明确说“别再问”后停止该话题，不可仅靠文字相似度重新激活。

普通跟进只在用户授权的话题内生成，受全局频率上限约束；同一话题不能因为用户未读而不断生成新消息。到期的一次性约定独立于普通频率上限，但同样只进入站内。站内消息应在服务端持久化，至少区分未读、已读、稍后与已处理；多次打开或多设备登录不重复生成。离线时不能查看最新站内内容，重连后同步；应用关闭期间不会有手机系统提醒。

**首版默认规则**：普通跟进每自然周最多 3 条、每天最多 1 条；同一话题两条之间至少 7 天，连续 2 次未获回应则暂停该话题，用户明确恢复或主动聊起该话题才重启。用户可在设置中调低或关闭普通跟进；“稍后”由用户选日期，到期更新原消息而不重复创建。判断到期按用户设置的时区（初次使用可取设备时区），显式约定的日期保留原时区语义；应用关闭时允许服务端记下到期事件，但不产生系统通知，打开后在站内收件箱显示未读标记，不强制弹出聊天框。明确约定的一次性提醒不占普通跟进额度，但由用户单独取消。

现有“每日定时提醒”继续保留。用户说“下周三问我面试怎么样”应生成**一次性约定**，不是创建每天重复的提醒。约定时间过去后才打开应用的用户，看到的是一条标注原定时间的未读站内消息，不能误称已准时通知。

### 9.5 Agent 内部操作与确认

操作提议与聊天回复分离，结构化展示操作类型、目标对象、拟修改字段及结果；有日期时间时显示时区。查询现有数据可直接回答并指出来源；任何写入或修改均需对该次具体操作单独确认。确认后由服务端执行，回复不能替代真实执行结果。确认卡过期或对象已被其他地方修改时，应重新获取状态并再次确认。

首版支持：新增/编辑待办，新增/编辑每日定时提醒，新增/编辑习惯，以及对指定日期和习惯的打卡/取消打卡；每日记录和记忆按前述专属确认流程。为降低误操作，删除待办、习惯和提醒先通过原有管理页面完成，不开放聊天中的自动删除。照片打卡仍由用户手动上传，不能因一句“我拍了”自动添加照片。

执行记录至少包含请求、用户确认、实际结果、对象标识和时间。提交超时或网络重试时不得重复创建；撤销只对可恢复的操作开放，并说明已发生的不可逆影响。确认前切换会话、退出应用或账号时，未执行的提议不得在后台自动执行。

## 10. 权限、数据与安全边界（建议口径）

| 数据或动作 | 可自动做 | 必须确认 | 用户控制 |
| --- | --- | --- | --- |
| 保存当前会话消息 | 登录后为提供会话体验而保存，首次使用前说明 | 不逐条弹窗 | 查看和删除会话 |
| 使用已确认的记忆辅助回答 | 在已授权用途内读取 | 超出用途时重新询问 | 查看、修改、删除记忆 |
| 生成每日记录草稿 | 可以 | 写入/覆盖之前 | 编辑、放弃、重试 |
| 提议长期记忆或关注点 | 可以 | 保存记忆或授权跟进之前 | 拒绝、停止、删除 |
| 读取 Today 内部事项 | 登录后在产品内查询 | 读取敏感范围的细则待定 | 查看来源及管理授权 |
| 修改 Today 内部事项 | 不可自动执行 | 每次具体写操作 | 查看执行记录、在允许时撤销 |
| 系统通知、外部应用操作 | 首版不支持 | 不适用 | 无须申请相应手机权限 |

对自伤、自杀等即时风险表达，应优先给出明确、适当地寻求现实帮助的建议，并提供当地可信求助资源的入口；不得推断诊断、承诺治疗效果或把危机内容自动加入长期记忆/后续问候。安全响应的地区适配、误判测试和人工评审是公开试用前的上线门槛，不能仅靠普通聊天 prompt 处理。

隐私需求包括：账号间严格隔离；对话与派生数据建立来源关系；逻辑删除立即阻断界面、检索、向量检索、缓存和后续生成，不能只隐藏列表项；删除与撤销的行为可被用户理解；服务端日志不得记录聊天正文、密钥或敏感原文。图片仅用于形象，替换/恢复默认后旧图不再可见或被引用；具体物理清除期限与备份处理未定前，不应宣称“永久保存”或“彻底无痕”。

## 11. 与现有实现的差异及建设范围

| 现状依据 | 目标与改造要求 |
| --- | --- |
| `CheckinAiPipeline` 提交后直接调用 `MemoryService.upsertFromCheckin` | 增加候选记忆与用户确认流程；同时覆盖手动记录与对话记录，避免绕过同意直接写库 |
| `ProactiveService.today` 可基于近期记录生成站内提示 | 将“主动跟进”与普通提示区分；没有话题授权不能生成待续消息；拒绝/停止要长期生效 |
| `reminders` 以 `HH:mm` 每日扫描，`reminder_deliveries` 按日期去重 | 支持一次性约定，保留每日提醒；到期写入站内收件箱，不能当成系统推送 |
| 现有 `checkins` 一人一天一条，AI 总结异步 | 复用一天一条和总结任务，但补充“对话来源、合并预览、版本/重试”语义 |
| 无移动端工程、会话消息表、形象配置及 Agent 操作记录 | 新增跨平台移动端与必要的服务端持久化；优先评估 React Native + Expo，共用一套业务代码 |

这些是需求上的缺口，不代表现有接口已经符合新规则。上线前需覆盖旧 Web 入口，否则同一账号可能在 Web 自动写入记忆而在移动 App 等待授权。

### 11.1 跨平台交付方案（建议）

建议新增 `apps/mobile`，使用 React Native + Expo + TypeScript 构建 Android/iOS 共用的移动端。保留 `apps/web` 作为已有 Web 入口，`apps/api` 继续作为统一后端；`packages/contracts` 的平台无关类型与校验可共享。优先共享 API 契约和纯业务规则，不承诺复用 Next.js 页面、DOM 组件或 CSS。选定具体 Expo 版本及构建方式前需做小型技术验证。

移动端直接访问可从手机联网的 HTTPS API 地址；现有 Web 的同源 `/api` 代理依赖 Next.js 服务端，不能作为 App 内的默认网络地址。鉴权凭据使用移动系统提供的安全存储方案，不沿用浏览器 `localStorage`；照片上传、图片展示、网络失败与恢复需分别在 Android/iOS 真机验证。首版不需要后台常驻任务或系统通知服务，站内跟进在服务端持久化、打开 App 时同步。

首个试用包可先发 Android，但从基础会话阶段就建立 iOS 构建和真机/模拟器验证：至少覆盖登录、文字聊天、站内消息、记录确认和返回导航。Android 与 iOS 用同一套产品规则；平台差异只允许体现在系统交互与必要适配。iOS 对外分发另需 Apple 开发者账号及对应的测试/上架流程，不把“可构建”误称为“已发布”。

## 12. 分阶段交付与验收（建议口径）

1. **基础会话与形象**：新账号自动呈现默认非真人形象；跳过自定义仍能聊天，上传裁剪/替换图片或恢复默认设置不丢历史；可查看/删除历史，切换账号不串数据，发送失败可重试。Android 真机可安装并完成登录到对话的完整流程；同期完成 iOS 构建与关键流程验证。
2. **记录与授权**：从对话确认写入今日记录并看到总结/时间轴变化；手动记录与对话都只能产生待确认记忆；拒绝后不写入也不反复提议。
3. **站内跟进与操作**：授权话题到期进入收件箱；应用关闭时无系统通知、重开后仍能看到未读；普通跟进受已确认的频率/未回应规则限制；确认创建待办/一次性约定/习惯操作后能在相应模块看到结果；失败不误报成功。
4. **试用门槛**：检查账号隔离、删除/撤销、安全响应、离线恢复、跨日与跨时区、消息去重和关键路径真机测试；提供 Android 试用包与故障反馈入口，再小范围开放。iOS 同期保持可构建、可运行；正式分发时间另定。

建议在试用阶段分别观察：首次打开到首轮对话的完成情况、主动自定义形象的比例；对话转记录的提议、编辑与确认情况；主动跟进被查看、继续、稍后或关闭的情况；Agent 操作确认后的真实执行成功率；以及被用户报告为打扰或错误记忆的案例。先建立基线，不把未经试用验证的指标写成既定目标。

## 13. 待确认的问题

- React Native + Expo 技术验证是否满足形象表现、照片处理与双端构建；如不满足，再评估替代跨平台路线。站内未读跟进如何持久化与同步需技术设计。交付顺序已定为 Android 小范围试用优先、iOS 后续发布，不把单纯的移动网页视为交付完成。
- 默认形象的具体视觉设计是什么？首版已确认支持用户上传图片、裁剪及替换，不依赖 AI 生图；支持的格式、大小、审核/违规处理与原图保留策略需在技术与安全评审时确定。
- 语音输入与播报留待后续版本，届时再评估权限、费用和形象表现。
- 普通站内跟进的默认上限和未回应暂停规则已确定；用户可选档位、时区与到期的边界细节需技术验证。
- 已确定会话逻辑删除和派生记忆/关注点清理；仍需确定逻辑删除后物理清除期限、备份处理、敏感信息范围及站内消息预览默认内容。
- 上线验收所需的可测指标和真实用户试用方案；此处不预设留存或站内跟进回应率数值。
