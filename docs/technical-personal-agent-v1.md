# Today Personal Agent 第一版技术方案（评审稿）

关联需求：[产品需求方案](prd-personal-agent-v1.md)。本文是拟实施设计，不代表接口、数据表或移动端已经实现。目标是 Android 优先试用、同一客户端代码可在 iOS 构建和验证；首版文字对话、用户上传静态形象、确认后写入、仅站内跟进。

## 0. 评审结论与开发前置条件

本方案可以作为开发基线，但以下事项必须先落地，不能等到移动端联调时再补：

- 会话删除依赖 `memory_sources` 等来源关系；在来源关系建立前不得开放会话删除，否则无法证明记忆和关注点的派生关系。
- 所有移动端写接口统一处理 `Idempotency-Key`/`clientRequestId`，不能只在契约中声明；重试必须返回首次请求的结果。目前会话创建、发送消息及行动页创建待办/习惯/提醒已用稳定请求 ID 防重复，其余写入口仍需逐项核对，不能视作已全部完成。
- 新增独立的 `conversation` AI 任务，输入包含受限的会话历史和已确认上下文，输出回复与结构化提议；现有 summary/memory/proactive prompt 不能直接当聊天接口。
- 跟进暂停依据必须来自可审计的用户事件（继续、已读、稍后、关闭），不能仅用一个计数猜测“未回应”。
- 对话生成采用可恢复的 `processing/succeeded/failed` 状态；同步请求超时不能触发第二次模型调用或重复写消息。首个垂直切片允许同步实现，但必须先落库幂等状态。

## 1. 方案结论

- 新增 `apps/mobile`，优先验证 React Native + Expo + TypeScript。Android/iOS 共用页面与业务状态；保留 `apps/web` 和 `apps/api`，复用 `packages/contracts` 的纯 TypeScript 契约。先做双端构建和真机网络/相册/安全存储验证，再锁定版本与组件库。
- 所有对话编排、授权检查、执行内部操作和跟进调度在 Spring Boot API 服务端完成。客户端只提交用户意图、渲染服务端的结构化提议并发送明确确认，不允许模型直接调用业务接口。
- MySQL 保存会话、消息、形象配置、同意/来源、提议与执行记录、关注话题和站内消息。复用现有 checkin、summary、memory、todo、punch、reminder 和 vector，但调整会绕过授权的旧入口。
- 应用关闭时不发系统通知、无后台常驻或远程推送。服务端可计算到期并保存站内消息，用户打开 App 时同步查看。对“定时提醒”不承诺应用关闭时准时触达。

现有 JWT 默认有效 168 小时且没有刷新令牌接口。首版可以在到期时保留本地未发送草稿并明确提示重新登录，重新登录后同步会话；不把过期 token 当成永久登录。是否新增刷新令牌需结合试用留存和安全成本另行评估。

移动端现在收到带令牌请求的 401 会返回登录页，预填原服务器和账号邮箱；离线或临时网络失败不会被误判为过期。本机草稿按服务器与账号隔离，不随令牌失效清除，重新登录原账号后恢复。正式试用仍需真机验证系统安全存储及过期期间的草稿恢复。

## 2. 已有能力和关键缺口

| 仓库现状 | 本方案处理 |
| --- | --- |
| `apps/web` 是 Next.js 页面，`/api` 由 Node Route Handler 代理；token 存在浏览器 `localStorage` | 移动端单独构建原生界面；通过 HTTPS 直连 API；token 放系统安全存储；Web 继续保留自己的代理 |
| `AiGatewayService` 仅有 `summary/memory_extract/proactive` 的结构化完成接口，缺少聊天能力 | 增加专门的会话生成与结构化提议入口，仍统一管理模型配置、超时、日志和限额；模型不可直写数据库 |
| `CheckinAiPipeline` 会在每日记录保存后自动 `upsertFromCheckin` | 将自动写记忆改为“提取候选 → 用户确认 → 写入”；手动 Web 入口和移动入口同一服务端规则 |
| `ProactiveService.today` 基于记录生成当天提示，未建模话题授权与未读收件箱 | 保留或调整旧提示，但不能未经授权生成长期跟进；新增跟进话题、调度及站内消息 |
| `ReminderService` 按 `HH:mm` 每日触发，缺少单次约定 | 保留每日提醒；新增单次约定模型，避免误用每日提醒 |
| `LocalMediaStorage`、`MediaController` 只支持 `punch/{userId}/...` | 为形象图片新增独立私有命名空间、上传校验和按属主读取；不放宽现有照片访问权限 |
| `FallbackVectorStore.delete` 可能吞掉主向量库删除错误 | MySQL 作为访问权限真相源；检索二次过滤失效记忆；向量删除/重建可重试和核对 |

不建议第一版把现有 Next.js 站点直接放入 WebView 充当移动端：页面和 API 代理依赖服务端运行，账号凭据及相册接入也需重做；这样不能省掉主要风险。最终技术选型以双端小型原型验证结果为准。

## 3. 模块与数据流

```text
apps/mobile (Android/iOS)
  ├─ 会话 / 确认卡 / 站内消息 / 形象编辑
  └─ HTTPS + Bearer ────────────────────────────────┐
apps/web (既有入口) ── /api 代理 ────────────────────┤
                                                   ▼
apps/api: identity + agent-conversation + proposal + followup + inbox
  ├─ ai-gateway → 模型（仅服务端保管 API key）
  ├─ checkin → summary → memory_candidates → memory(已确认)
  ├─ todo / punch / reminder（复用服务层，做属主校验）
  └─ MySQL（权威状态） → 可选 Qdrant（辅助索引）
```

一条对话的顺序：保存用户消息（带幂等键）→ 读取当前会话与已确认且有效的记忆/授权话题 → 安全检查 → 模型生成回复及**候选**提议 → 保存回复和提议 → 客户端显示。确认写入需单独调用服务端 `confirm`，由服务端重新验证用户、版本和授权，再执行操作并返回真实结果；自然语言的“好的”不能代替确认按钮。

聊天的只读上下文现在还包含本人已保存的今日记录，以及最多 5 条排除当天的近期时间轴摘要（取 6 条后过滤，每条摘要最多 160 字）。这些记录不是长期记忆授权，也不能单独触发记忆、跟进或操作提议；用户询问更早日期时需说明当前输入的时间轴范围，不应编造未提供的记录。

创建待办、习惯和每日提醒的模型候选还须通过服务端对本轮用户消息的明确创建意图校验；常见否定句（如“不要添加待办”）抑制对应创建卡，其他明确请求的操作不受影响。规则式校验不能完整理解反讽、引用、跨句否定和复杂组合意图，正式试用前需用真实模型对话集评估误触发与漏触发；确认按钮和业务层授权校验不能因此省略。

单次预约也复用提醒意图与常见否定句校验；模型不能仅因为本轮出现“不要提醒我”就生成预约确认卡。已生成的预约仍要通过用户明确确认、时区和有效日期检查。

单次预约还要求用户本轮原话出现具体钟点或明确的分钟/小时后等相对时间；只有“明天提醒我”“明天上午提醒我”时，不接受模型擅自填入的时刻，应由 Agent 询问具体时间。这是原话的最低限度校验，不保证解析出的日期/时刻与原话一致；确认卡必须展示本地时间和时区供用户核对，真实模型联调需覆盖跨日、模糊时间和相对时间。

同一会话中已拒绝的跟进候选，会按保存的完整缘由文本阻止后续相同提议；查询限定当前用户和未删除会话。不同措辞描述同一话题仍可能再次出现，不能将文本相等去重视为语义级拒绝记忆；正式试用前需评估话题身份与用户重新授权的交互。

模型失败或未配置可返回清晰的“暂时无法对话/请稍后重试”；现有 heuristic 总结降级不等于合格的情绪陪伴对话，不应伪装成模型回复。用户消息可在待重试状态保留，但不能重复执行操作。

## 4. 数据模型建议

所有新表包含 `user_id`、创建/更新时间和合适的 `deleted_at`，所有查询及异步任务均按属主与有效状态过滤；重要状态迁移留操作审计。表名、字段为逻辑草案，迁移脚本实现时再确定具体 SQL。

| 数据 | 建议关键字段与约束 | 用途 |
| --- | --- | --- |
| `agent_profiles` | `user_id` 唯一、`name`、`tone`、`avatar_media_id`、`version` | 默认形象或用户自定义；更新不影响会话 |
| `agent_media` | `user_id`、`private_path`、`mime`、`size`、`status`、`replaced_at`、`next_cleanup_at` | 上传形象图；独立于习惯照片；旧图失败后延时重试，避免积压文件阻塞后续清理 |
| `conversations` | `id`、`user_id`、`status`、`deleted_at`、`version` | 会话逻辑删除及并发控制 |
| `conversation_messages` | `id`、`conversation_id`、`role`、`body`、`client_message_id`、`status`、`deleted_at`；`(user_id, client_message_id)` 唯一 | 消息幂等、顺序和失败恢复 |
| `agent_proposals` | `id`、`source_message_id`、`kind`、`payload_json`、`status`、`expires_at`、`target_version`、`confirmed_at` | 记录、记忆、关注点和工具动作的待确认提议 |
| `agent_action_logs` | `proposal_id` 唯一、`user_id`、`kind`、`target_id`、`result`、`executed_at` | 用户确认到真实执行的可审计结果 |
| `memory_sources` | `memory_id`、`source_type`、`source_id`、`consent_id`、`active` | 删除会话时识别仅由该会话派生的记忆 |
| `followup_topics` | `user_id`、`source_conversation_id`、`reason`、`consent_id`、`state`、`next_eligible_at`、`unanswered_count`、`last_delivered_at`、`version` | 已授权的普通跟进；停止后不得自动复活 |
| `one_off_appointments` | `user_id`、`source_id`、`due_at_utc`、`original_timezone`、`status` | 用户明确约定的单次站内提醒，不复用每日提醒 |
| `inbox_items` | `user_id`、`kind`、`source_kind`、`source_id`、`scheduled_at`、`state`、`read_at`、`snoozed_until`、`deleted_at`；`(user_id, source_kind, source_id, scheduled_at)` 唯一 | 持久化未读及重试去重 |
| `followup_preferences` | `user_id` 唯一、`timezone`、`max_per_day`、`max_per_week`、`enabled` | 默认频率和用户关闭/调低设置 |

现有 `memories` 和 `checkins` 需增加来源/状态/版本关联，或通过独立关系表维护。不能只靠模型摘要或 `memory_text` 反推来源。对于多来源记忆，移除被删会话的来源；只有剩余独立来源和明确确认仍有效时才保留，否则失效。用户明确确认生成的每日记录、待办和打卡不随会话删除自动删除，其来源引用需标记为已删除，避免再链接到敏感原文。

逻辑删除不是物理清除的替代承诺：数据库/备份实际保留期限、彻底删除流程和恢复策略需要单独决策。首版不宣称“已彻底擦除”。

新增表和旧表字段要同时纳入 `db/schema.sql`、增量迁移脚本、启动校验及 `scripts/db-init.sh` 的校验清单。`SchemaBootstrap` 对自动迁移 SQL 仍允许部分失败，但现在会验证关键表、授权/删除列和幂等唯一索引；校验失败时阻断 API 启动，关闭自动迁移也不能跳过校验。上线部署按“先迁移、校验、再启用新行为”执行，并为旧 checkin 数据提供来源未知的历史标识。

## 5. API 契约草案

路由沿用 `/v1`；请求与响应的 Zod 契约放 `packages/contracts`，Java DTO 与其对齐。所有对象 ID 均按当前用户查找，缺少权限时统一返回不可见而非暴露他人信息。`POST` 写操作需要 `Idempotency-Key` 或稳定 `clientRequestId`；重试返回同一最终结果。

| API 草案 | 主要行为 |
| --- | --- |
| `GET/PUT /v1/agent/profile`、`POST /v1/agent/avatar`、`DELETE /v1/agent/avatar` | 默认配置、编辑、受保护上传/恢复默认；图片读取使用鉴权接口 |
| `GET/POST /v1/agent/conversations`、`GET/DELETE /v1/agent/conversations/{id}` | 列表、创建、查看及逻辑删除会话 |
| `GET /v1/agent/conversations/{id}/messages` | 按 `before`（ISO 时间）与 `beforeId`（消息 UUID）分页取更早消息；返回 `messages` 和 `hasMore`，同毫秒消息不会跳过 |
| `POST /v1/agent/conversations/{id}/messages`、`POST /v1/agent/conversations/{id}/messages/{messageId}/retry` | 保存用户文本、生成或显式重试 Agent 回复，返回消息、状态及候选提议；超时可用同一消息 ID 安全查询或重试 |
| `POST /v1/agent/proposals/{id}/confirm`、`POST /v1/agent/proposals/{id}/reject` | 确认/拒绝单项提议，`confirm` 返回真实执行状态或版本冲突 |
| `GET/PATCH /v1/agent/followups/preferences`、`GET /v1/agent/followups/topics`、`POST /v1/agent/followups/topics/{id}/stop|resume` | 查看已授权和暂停的话题、显式停止/恢复、调整频率和时区；已删除来源不可恢复 |
| `PATCH /v1/agent/followups/topics/{id}` | 编辑已授权话题的缘由和可选下次跟进日期；附原缘由与原时间快照，冲突返回 409 |
| `GET /v1/agent/inbox`、`POST /v1/agent/inbox/{id}/read|snooze|dismiss|continue` | 站内消息、未读数及状态变更；稍后更新原条目 |
| `GET /v1/agent/actions`、`POST /v1/agent/actions/{proposalId}/undo` | 查看本人近期操作；对仍未被后续修改的待办/习惯/每日提醒编辑执行撤销 |

形象图上传采用 `multipart/form-data`；客户端从相册选择并本地裁剪/预览，服务端重新校验实际文件类型、大小和像素数、重新编码去 EXIF，写入私有路径。仅 `user_id` 属主可取；替换时先保存新图并更新配置，旧图清理异步可重试。初期可沿用现有本地持久化目录，但需单独容量、备份、鉴权与过期清理策略；日后再抽对象存储接口。格式/上限的具体数值待技术验证。

当前上传使用按用户隔离的 `Idempotency-Key` 和图片 SHA-256 校验；相同键/相同图片的重试读取原结果，不再次写媒体或占用限额，相同键/不同图片返回 409。移动端先复制裁剪图到按服务器及账号隔离的 App 私有目录，再将请求 ID 写入安全草稿；只有持久化成功才可上传。超时与重启后复用同一图片和请求 ID，图片丢失时提示取消并重选，成功后重新读取当前资料，以免旧重试结果覆盖其他设备较新的形象。替换/取消/恢复默认时清除对应本机草稿；恢复草稿时清理同账号孤立的本机形象图片，不触及打卡照片。

上传与恢复默认都在事务内锁定 `agent_profiles` 用户行，然后切换引用、将旧媒体标记为 `replaced`；并发操作按提交顺序生效，异步清理器只删除 `replaced` 文件。独立 MySQL 并发测试覆盖上传持锁时重置等待及最终引用一致性。

## 6. 关键一致性与授权流程

### 6.1 对话整理与记忆

会话消息可以保存以恢复聊天，但**保存会话 != 保存长期记忆**。从对话或手动 checkin 提取的记忆先落候选；预览中明确“记录正文”和“拟保存的记忆”是两次独立确认。提交 checkin 后异步生成总结及待确认记忆候选，不直接 upsert 长期记忆。所有写入口（含旧 Web）切换到同一规则；已有记忆迁移时保留历史标记，不能伪造新授权。

用户本轮明确表达“不要记住”“别再跟进”等拒绝时，在消息入库的同一事务内撤销该会话尚未确认的对应提议，即使模型随后超时也生效；模型返回同类候选时仍由服务端过滤。这是针对明确措辞的兜底，不代表能识别所有自然语言变体；已确认的记忆和已授权话题不能仅凭模糊措辞猜测删除，应通过现有管理入口按对象处理，上线前继续评审这一体验。

对同一天 checkin 采用按版本写入：用户确认预览时提交原版本；版本不匹配则要求重新查看合并结果。总结任务携带 checkin 版本，落库前核对版本；晚到的旧任务不能覆盖新总结。时间轴始终按最新有效版本读取。日期根据用户选定时区确定，跨日时在确认卡上显示目标日期。

当前实现已提供 `checkin` 对话提议：服务端按用户时区选择目标日期，显示原话、已有正文和合并预览；`PATCH /v1/agent/proposals/{id}/checkin-preview` 可编辑正文、换日期或重新获取预览。确认时锁定该日记录并比对预览时 `updated_at` 与原正文（防同毫秒更新漏检），冲突返回 409，重新预览后再确认；成功才入队日总结及待确认记忆候选。记录日期目前限定为用户当地今天及过去 30 天，后续可结合实际回填需求调整。

### 6.2 内部操作

模型只输出经过允许列表校验的结构化提议（类型、目标、参数），服务端填入当前对象快照并生成确认卡。用户确认时校验提议归属、未过期、未被拒绝、目标版本未变化；在同一数据库事务内使提议只可确认一次并执行 Todo/习惯/提醒写入，写操作以 `proposal_id` 唯一。对媒体等非事务步骤使用“先保存，确认后切换引用”的状态机。失败写真实错误并支持安全重试；不得先回复“已完成”再尝试执行。

当前对话的 `todo_edit` 已接入：只发送最多 20 条本人待办摘要给模型；候选 ID 必须属于这批可见待办，卡片展示原值与新值。确认时锁定待办并核对标题、备注、状态、截止日期及更新时间；中途修改返回 409，原提议不执行，用户可重新描述修改。创建与编辑复用 `TodoService`，操作日志记录实际目标 ID。

对话习惯编辑与打卡/取消打卡已接入：模型只读取最多 20 条本人习惯摘要，编辑提议必须指向可见习惯并显示名称、描述或启用状态的前后变化；确认时锁行校验完整快照，变化返回 409。打卡提议还须注明用户当地日期（限定今天至过去 30 天），卡片显示习惯、日期以及取消时照片会被删除的提示；确认时锁定习惯与当日记录并核对标题、状态、更新时间、打卡 ID 及备注/照片指纹。照片取消时在同一数据库事务中入清理队列，提交后后台删除，失败按租约重试；读取须有有效打卡引用。文字打卡不会虚构或上传照片。

每日提醒编辑也已接入：模型只读最多 20 条本人提醒摘要，修改标题、内容、每天触发时间、时区或启用状态时，确认卡列出前后变化。确认时在数据库事务内锁定原对象并核对完整快照；旧投递记录仍保留原内容，不随编辑回写。用户未要求修改的字段保持原值；该操作不转换为一次性预约或系统推送。

上述三类编辑在确认时保存编辑前后快照。操作记录提供撤销入口；撤销在同一事务内锁定本人操作与目标，核对目标仍是该次编辑后的版本，再恢复编辑前字段并记录撤销时间。目标被删除或之后由用户/Agent 修改过则返回 409，不能覆盖后来的内容；重复撤销返回同一结果。创建、打卡、旧版无快照操作不可撤销，已投递的提醒也不会因撤销设置而被撤回。已有库先执行 `migration-agent-action-undo.sql`；隔离库 HTTP 用例覆盖三类编辑及并发冲突。

移动端“行动”页新增待办/习惯/每日提醒视图；习惯可从相册选择、预览并手动上传照片打卡，删除习惯前明确显示打卡记录及照片会一起删除。删除时锁定习惯，在同一数据库事务中删除关联打卡并加入持久化照片清理队列；常规照片替换和取消打卡也在事务中入队。后台按租约重试，但物理文件与备份的清除时限仍需单独确定。

“行动”页的待办复选框改为提交明确的 `open/done` 目标状态，不再调用翻转接口；超时后重复发送同一目标不会反向撤销操作。旧 `toggle` 路由仍为兼容保留，不应作为移动端重试路径。

行动页创建待办、习惯和每日提醒会传 `Idempotency-Key`；服务端在同一 MySQL 事务内记录请求摘要和首次响应，按用户、创建类型和请求 ID 唯一约束并发重放。原样重试复用 ID，修改表单内容则换 ID，旧版无请求头客户端仍可使用。待创建表单和请求 ID 按服务器与账号写入系统安全存储，进程重启后恢复；发送前等待草稿写入成功，读取损坏或写入失败时暂不发送创建请求。确认成功或明确取消后清理相应草稿。系统安全存储的真机恢复和极端进程终止时机仍需真机验证。

行动页文字与照片打卡也使用请求 ID：同一张照片重试不会二次替换，服务端对图片字节和字段摘要检查同键冲突；上传后数据库事务回滚会立即清理新文件，删除失败则在新事务持久化清理任务以便重试。移动端在上传前将处理后的照片复制到按账号及服务地址隔离的 App 私有持久目录，安全草稿只保留习惯、日期与请求 ID；重启后校验文件并使用原 ID 重试，文件丢失则阻止上传并提供取消草稿入口。成功、取消、替换和清除草稿后清理文件，恢复时清理无引用的旧照片。跨重启恢复已有本地单测，仍需真机验证系统清理、账号切换和上传成功但响应超时的实际体验。旧客户端无请求头仍可提交，需继续审计其他写入口。

手动每日记录也使用请求 ID：服务端在同一事务内保存正文、AI 任务与首次响应，同键同正文重放返回首次结果，不会再次更新记录或重跑总结；同键不同正文返回 409。今天页在系统安全存储中保存草稿正文及其 ID，正文变更时换 ID，提交前确保草稿落盘；读写失败阻止发送并提供重新读取或确认清除。旧草稿在首次提交前补齐请求 ID；服务器记录期间变化时需重新确认并换 ID。无请求头的旧客户端仍兼容。真机安全存储与跨午夜恢复仍需验证。

### 6.3 站内跟进

默认每用户的本地自然周最多 3 条普通跟进、自然日最多 1 条、同话题至少间隔 7 天；连续 2 次消息未获继续聊/稍后等回应，该话题暂停。第二条即使仍未读，达到下次可跟进时间时也会暂停；用户仍可从原站内消息继续聊并恢复该话题，选择“稍后”则清除未回应计数。用户手动停止会关闭对应消息，不会被旧消息自动恢复。用户可调低或关停；单次明确约定独立计数，但可单独取消。普通跟进必须有已确认的话题及来源，禁止仅凭原始聊天自动投递。

当前服务端已支持按账号列出已授权/暂停话题，移动端收件箱可在首次投递前停止话题，也可显式恢复；恢复时沿用更晚的原计划、同话题最短间隔，并至少推迟到次日。来源会话已删除的话题不可列出或恢复。

服务端周期扫描已授权且到期的话题；在 MySQL 事务中锁定话题与偏好、核对时区、频率、拒绝/暂停状态，插入唯一键约束的 `inbox_items` 并更新 `last_delivered_at`。并发部署时依赖条件更新/锁及唯一键防重；进程重启后可补扫。到期但超出频率上限时**跳过或延后并重新评估**，不在下次打开时堆积旧消息。过期的一次性约定只生成一条并标注原定时间。打开 App 时拉取增量未读，不用系统推送，也不自动弹出聊天框；站内消息仅可引用未删除的来源。

“无回应”按该话题投递后的用户行为计，不把网络失败或用户未打开 App 简单当成拒绝；具体暂停点在测试中覆盖。`snooze` 不创建第二条消息。用户手动关闭话题或删除来源后，再次扫描必须不可投递。

用户可在收件箱编辑已授权话题的缘由和下次可跟进日期；日期按设置时区的当地 09:00 解释，限制在未来 30 天内，且不能早于同话题上次投递后的 7 天。编辑时锁定有效来源与话题并比较原缘由/原时间，过期视图返回冲突；相同目标重试不重复改动。暂停或已删除来源的话题不能编辑，需先明确恢复暂停话题。

站内消息的“继续聊”在首次响应丢失后可重试：同一消息已经 `handled` 且来源仍有效时返回原会话，不重复改变话题计数或投递时间；手动停止或删除来源后仍不得通过旧消息继续。并发请求在话题锁之后读取最新消息状态，避免在 MySQL 可重复读快照下把成功重试误判为 404。

“标记已读”和“关闭”重复提交相同目标状态时返回已有结果，不刷新已读时间，也不重新开放已处理或已关闭消息；按账号隔离仍须生效。

全局关闭跟进或上一条仍未读/稍后时，已到期的话题延后一天复查，不新增站内消息；这也使扫描上限内的旧话题不会长期挡住其他用户。用户重新开启跟进后仍需遵守原频率与同话题间隔。

### 6.4 逻辑删除与索引清理

会话删除在 MySQL 事务内：标记会话/消息 `deleted_at`，拒绝待确认提议，失效仅源自该会话的记忆/关注点及待发送消息，取消相关作业和一次性约定；多来源记忆按来源规则处理。所有 API、上下文构建、摘要/候选生成和站内收件箱读取必须按有效状态过滤。已经独立确认的记录/待办继续保留，但不能继续引用被删原话。

事务提交后异步删除或禁用 Qdrant 向量与缓存；失败时持续重试并可审计。由于现有向量层可能吞下删除失败，检索命中后还须回表检查 `user_id` 和未删除/已确认状态，MySQL fallback 也只搜有效数据。运行中的 LLM/总结任务写库前再验来源版本和删除状态；删除后不允许晚到结果重新创建记忆或消息。后台清理和重建索引仅以数据库有效集合为准。

当前实现新增 `vector_sync_jobs`：记忆变更在同一 MySQL 事务内入队；后台按最新数据库行决定严格更新或删除 Qdrant 点，失败按租约和版本重试。接口读取先由 MySQL 的归档/属主条件阻断，不等待外部索引完成；多实例中晚到的旧任务会重新排队修正最新状态。物理清理的时效与备份保留仍需单独约定。

会话创建现已接受可选 `clientRequestId`（兼容旧客户端），移动端创建首条消息前使用消息 ID 派生稳定的创建请求 ID；数据库 `(user_id, client_request_id)` 唯一约束保证超时重试不会新增空会话。已删除会话的同键重放返回 409，不能恢复；没有请求 ID 的旧客户端仍不能保证创建幂等。上线迁移须执行 `migration-conversation-create-idempotency.sql`，并由启动校验确认列和唯一索引存在。
新建会话另设每账号每天 60 次的默认上限（可配置），在事务中仅对首次落库的会话计数；同一请求 ID 重放不再次占用额度，也不影响单独的模型调用限额。

历史对话目前提供独立的消息游标分页接口：默认先读取最新 50 条，App 的虚拟化列表按需加载更早消息。游标同时包含创建时间和消息 ID，服务端按属主及未删除状态查询；新回复或轮询刷新时，客户端保留已加载的历史片段。

移动端对话草稿在系统安全存储中保留正文、原消息 ID 与已创建的会话 ID。读取格式损坏或安全存储写入失败时暂停发送，允许重新读取/保存，或由用户明确确认清除；不会静默分配新的消息 ID。网络失败后原消息 ID 不变，服务器确认消息成功后先清除本机草稿再清空输入框，避免清理失败时丢失重试依据。真机进程终止、账号切换和系统安全存储恢复仍需验收。

## 7. 安全、隐私与可观测

试用反馈使用独立的 `feedback_reports` 表与 `/v1/feedback` 接口：账号隔离、默认 24 小时最多 5 次、提交带幂等键。仅传用户填写的类型与正文，不自动附带会话、照片或设备日志；移动端在 SecureStore 保留按账号及 API 地址隔离的待提交正文和请求 ID。删除时事务内逻辑删除反馈并将对应 `create_requests.response_json` 改为只含 ID；保留键防止重放重新写入，重放已删反馈返回 409。部署前执行 `migration-feedback-reports.sql`，已有库也须具备创建幂等和限额表。原反馈表中正文仍属于逻辑删除数据，物理删除期限及备份策略尚待上线前明确。

- 模型只接收当前请求必要的消息与用户明确确认的记忆；用户关闭或删除的跟进话题不得再次注入上下文。API key 仅放服务端；外部模型供应商的数据处理与隐私告知在试用前明确。
- 情绪陪伴有单独的安全响应策略：识别到的即时危机内容走确定性安全分支/资源指引，不让模型提出长期记忆、主动跟进或操作建议，并在后续普通对话的模型上下文中过滤该轮危机消息。当前规则只覆盖一部分明确表述；上线前必须对漏判、误判和地区资源做人工安全评审，不能把规则命中率当作诊疗能力。不宣称诊断或治疗。
- 图片校验真实内容、像素和大小，限制解码资源消耗；私有路径需用户鉴权，不接受任意路径读取。允许用户更换、恢复默认；旧图在引用失效后清理。图片审核策略需产品和合规评审。
- 聊天正文和上传图片不进入 AI 调用审计、普通访问日志或异常堆栈；日志记请求 ID、耗时、任务类型、状态与错误码。AI 失败、提议确认、跟进去重、删除清理、向量重试分别可观测，隐私敏感内容需脱敏。
- 服务端校验所有者与授权，客户端不能通过篡改提议 payload、过期 ID 或重复点击绕过确认。限流覆盖注册、登录、聊天、上传与提议生成，限制长会话上下文与模型成本。

## 8. 交付顺序与验证

1. **技术探针**：创建可运行的 Android/iOS Expo 空壳，验证 workspace 契约导入、HTTPS 请求与安全存储、相册选择/裁剪/上传及两端构建。若原型失败再比较替代跨平台方案。
2. **服务端底座**：新增表及迁移、会话与形象、幂等消息、统一 AI 对话网关、安全策略；在 API 单测和数据库集成测试中证明账号隔离与重试行为。
3. **授权和旧链路迁移**：checkin 自动记忆改候选/确认，Web 与移动端一致；处理来源关系、删除与向量重试；测试旧任务晚到、删除竞态和重建索引。
4. **操作与站内跟进**：提议确认执行、单次约定、收件箱与频率调度；验证并发扫描去重、时区边界、停止话题和应用关闭后重开。验证迁移中断或关键表缺失时功能拒绝运行，而非静默沿用旧授权规则。
5. **移动端完整体验**：默认/上传形象、文字聊天、确认卡、今天/回看/行动/收件箱；Android 真机回归，iOS 模拟器及真机关键路径回归。先发 Android 小范围试用，iOS 发布另走签名与分发评审。

每阶段保留最小端到端场景，最终至少验证：聊天失败重试不重复消息；确认写入前库里无新记忆；同一天补充记录不增加时间轴卡；删除会话后记忆检索与晚到任务都不复活派生数据；3/周、1/天、7 天同话题、2 次未回应暂停；应用关闭期间无系统通知而重新打开可见站内未读；双端图片和登录可用。

## 9. 上线前需拍板

- 上传图片的尺寸/格式上限、内容审核、旧图清理与存储备份策略。
- 逻辑删除后数据库及备份的物理清除时限、是否允许恢复会话；隐私说明按实际能力撰写。
- 首批试用用户与 iOS 测试渠道、模型供应商和对话成本预算；无模型 key 时聊天功能不可用应有明确提示。
- 跟进用户可选档位、旅行时区切换策略、长期未打开应用后的旧站内消息呈现；上述细节不改变已定默认频率与“不推送”的产品边界。
